# 字幕批量质检与执行记录

本文件是[口播剪辑Skill](../SKILL.md)的工具操作说明。语义、样式、参数和结果判定仍读Skill及[剪辑执行标准](剪辑执行标准.md)。工具只读取用户提供的媒体、字体和证据，写入指定的本地记录；不控制软件、不清理文件、不提交发布状态。

## 调用位置与依赖

内部从经营系统根目录调用`tools/<脚本>`；独立安装从Skill目录调用`scripts/<脚本>`。以下示例使用内部路径；文件名均为使用者本条产物。Python3标准库负责记录、容量与文件检查；字宽和像素检查还需Pillow。抽帧、文件探测、完整解码和容器修正使用本机已可用的FFmpeg/FFprobe，可用`--ffmpeg`、`--ffprobe`指定路径；本工具不安装剪辑引擎，不携带字体、人物素材、私人转写、校准样张或运行记录。

## 字幕：文字与时间、几何与字形分开验证

1. ChatCut提供最终保留文字与最终速度下的词头时间。执行者先按完整意思分卡，再用`check_subtitle_width.py`按剪映目标字体测宽，输出计划SRT。不能按固定字数截断，不能让ChatCut的预览字体代替剪映字体。
2. 正式导出时另导出当前剪映原生SRT。`check_subtitle_render.py scan`先逐卡核对计划SRT与原生SRT的文字、数量和真实起止时间（只容许毫秒取整误差），再核对实际成片。文字不一致先处理交接差异，不把OCR当作校正稿。
3. 实际画面检测使用字体校准后的白色静态字幕像素与字形。它核对行数、位置、安全边界、漏显及明显字形差异；手势、麦克风反光或栅格差异可能产生疑点，进入集中复核。语义完整、实际说出的词、音画同步、人物与动画合成及整条实播分别核验。

### 配置与首次验证

沿用字宽配置的字体文件及SHA256、实际像素字号、画幅、安全边界、锚点、余量、缩放和字距，增加`render`对象：

```json
{
  "canvas_height_px": 1920,
  "crop": [0, 1240, 1080, 400],
  "scan_band_px": [90, 310],
  "expected_center_y_px": 200,
  "center_tolerance_px": 8,
  "white_threshold": 220,
  "max_channel_difference": 30,
  "row_min_pixels": 10,
  "row_join_gap": 8,
  "row_min_rows": 6,
  "row_padding": 3,
  "shape_f1_min": 0.98
}
```

这些值仅展示schema，不是其他素材的默认参数。`crop`为成片坐标中的左、上、宽、高；`scan_band_px`和中心纵坐标相对于裁片。用本条原生代表画面确定阈值、字幕带、误差与字形相似度，不能改阈值只为消除当前疑点。`calibration_ref`指向原生字段及校准证据文件，配置必须标记已校准。字体文件SHA、配置、校准证据和检测脚本变化都使旧验证失效。

`samples.json`为列表，每项含`path`、`text`、`expectedLines`；必须包含真实剪映单行及折行样张，至少一个单行项含`wrongText`，用于同字数错词对照。执行：

```bash
python3 scripts/check_subtitle_render.py validate --profile render-profile.json --samples samples.json --output validation.json
```

工具验证原生单行正常、原生折行可检出，以及明确标为合成的漏显、水平越界、纵向移位和错词对照。不把合成控制说成真实剪映失败案例，也不把少量校准说成任意字体/背景均可用。当前检测限白色静态字幕、已验证字体及正常缩放/字距；新颜色、动态字幕、不同字距/缩放、字体缺字或字幕带无法分离时，先补相应验证，不能照搬旧配置或交给几百张人工识别兜底。

### 全量扫描与疑点复核

```bash
python3 scripts/check_subtitle_render.py scan --video final.mp4 --srt planned.srt --native-srt native.srt --profile render-profile.json --validation validation.json --output-dir caption-qc
```

先探测少量首尾、长短和混排卡，再批量抽取每卡稳定帧。实际视频必须与配置画幅一致、零起点且恒定帧率；时间码取真实帧，不从卡号估时。探测大面积几何失败即停止，避免把检测器错误变成整条逐卡返工。OCR只可作另行验证后的辅助；OCR引擎异常先停该分支，不触发逐卡重试。

产物为`report.json`及带时间戳历史、全卡覆盖清单、带哈希的抽帧缓存和每页12张疑点拼图。退出码0仅为该检测范围完成，1为存在待复核疑点，2为配置/输入/检测失败；错误会覆盖最新报告为失败，旧绿灯不能代表本次。缺帧、抽帧不全、SRT差异、旧配置或字体缺字均不能默认为通过。

人工在拼图中集中复核疑点，必要时打开原始裁片与完整合成画面。确为误报时，将`report.json`的`signature`原样放入复核JSON，每项`reviews`写入`id`、对应`frame_sha256`、`disposition="false_positive"`、具体`note`及可达的`evidence`文件，再执行：

```bash
python3 scripts/check_subtitle_render.py scan --video final.mp4 --srt planned.srt --native-srt native.srt --profile render-profile.json --validation validation.json --output-dir caption-qc --reuse-frames --review review.json
```

同一媒体、字幕、配置、校准和检测脚本哈希全部匹配，且全部帧文件及描述匹配，才能复用抽帧；复核还必须绑定同一签名和对应帧哈希。已有视觉复核只在像素文件完全一致时可引用。真实错误回当前可编辑工程局部修复，重导后用新目录检测；新文件不会沿用旧绿灯。静态中点不覆盖入退场、语义、实际听辨与人物/动画遮挡，这些项目保留独立检查证据。

## 单份记录与按需诊断

普通制作只维护本条已有run，引用原片/工程标识、当前转写和保留清单、已选源区间、实际时间线、字幕映射、检查结果和关键保存时点。现有工具生成的哈希与清单直接复用；内容真实变化才更新相应修订及失效范围，不每个阶段再建快照，不人工逐词填表，不因仅改显示样式而重做语义剪辑。历史依据保持可追溯，记录集中不等于覆盖旧证据。

返修在同一run写实际变化项、继续有效项和证据引用，只补受影响项；文件检查不能自动证明原生轨道、像素、音轨或听感未变。普通制作不要求独立回归表。新旧对照图、工具性能对照和脚本回归仅属工具升级验证，不进入每条视频的日常步骤。

只有来源错配难以定位或已触发音频诊断时，才选择已有的可选工具。独立安装将下面的tools/替换为包内scripts/；不要把这些命令当成依次执行的清单：

```bash
python3 scripts/check_video_revision.py snapshot --revision r1 --source main=原片.mp4 --input timeline=after-speed.json --input timeline_check=timeline-check.json --output diagnosis-r1.json
python3 scripts/check_video_revision.py audio --snapshot diagnosis-r1.json --audio 当前实际导出的.wav --timeline-check timeline-check.json --output audio-diagnosis-r1.json
python3 scripts/check_video_revision.py compare --before diagnosis-r1.json --after diagnosis-r2.json --unchanged timeline --output unchanged-diagnosis.json
```

snapshot仅绑定实际输入；compare仅比较明确要求不变的已提供资料，不能给本来就请求改变的角色填写unchanged。音频工具仅适用于当前支持的完整PCM WAV与其实际对应的数值时间线；局部音频不得套整条时长，应提供对应局部依据或另行核对真实范围。必须有当前项目/时间线的实际音频导出请求、完成响应和文件，不拿旧等长音频替代。audio_clock_checked仅表示WAV完整、非完全静音且时钟相符，实际听辨仍为NOT_PERFORMED。无法实际听辨时不为完成形式预审生成WAV；最终成片检查不取消。

## 包装证据清单与检查点

在本条已有run JSON内写入`editingExecution`，不另建第二套状态库。`requirements.json`必须显式含九项：`speed`、`voice`、`beauty`、`body`、`grade`、`subtitles`、`identity`、`animation`、`cover`。每项为`{"required":true,"target":实际目标JSON}`；不适用为`{"required":false,"reason":"本次范围依据"}`。目标来自当前Skill与本人范围，不由脚本发明。

```bash
python3 scripts/manage_video_editing_run.py init --record run.json --revision r1 --requirements requirements.json
python3 scripts/manage_video_editing_run.py verify --record run.json --key beauty --actual actual-beauty.json --evidence native-readback.png --scope '当前实际工程及全部受影响人物片段的原生回读'
python3 scripts/manage_video_editing_run.py checklist --record run.json
```

`actual-*.json`是实际重新选中对象后的回读值；每项还要记录作用范围及证据文件SHA。单张截图不能自行证明整轨生效，执行者仍须核对覆盖清单。缺证据、目标不符、证据文件变动都会保留未完成；退出码1不得推进包装门。`packaging_record_complete`只证明记录齐全，不证明截图内容真实，也不替代资源、文件、实播或本人采用。

新建草稿/修订重新初始化；同一草稿的局部变化用`invalidate --record run.json --key subtitles --reason '本轮实际变化'`使受影响项失效，再补验。没有变化的有效检查点保留，禁止清空记录重填假通过。

## 速度、时长与源区间校验

`check_video_timeline.py`只检查指定主口播轨，不改工程。改速度前先保存完整ChatCut时间线JSON及已选源区间；`timeline.json`采用实际`entries`结构，每项含`id`、`itemType`、`trackAlias`、`asset.id`、`sourceRange.start/end`（微秒）、`timelineRange.fromFrame/toFrame`。按实际主轨别名与fps调用，不把MG或B-roll轨混入：

```bash
python3 scripts/check_video_timeline.py capture --timeline before-speed.json --track V1 --fps 30 --output source-plan.json
```

随后按当前MCP schema成组更新倍速、时长和后续开始帧。目标帧数为`锁定源时长秒 / Skill目标倍速 * 实际fps`四舍五入；不以修改后被自动扩展的源区间重新计算。成组读取新时间线及每个口播item的实际字段。`readbacks.json`为`[{"id":"完整itemId","data":{"playbackRate":目标值,"durationFrames":实际帧数,"startFrame":实际开始帧,"sourceIn":实际源起点微秒,"assetId":"实际资产ID"}}]`；不把计划值填进回读。`sources.json`为`{"完整assetId":{"durationUs":原素材实测时长微秒}}`。

```bash
python3 scripts/check_video_timeline.py check --timeline after-speed.json --readbacks readbacks.json --plan source-plan.json --sources sources.json --target-rate 1.1 --output timeline-check.json
```

工具逐项核对目标倍速、帧数、顺移、源起点/终点与原文件边界，并绑定所有输入SHA。退出0表示数字检查完成；退出2或`errors`非空不得交接。特别检查“速度已改，但原时长未改，API据新速度自动扩展源终点”的情况；修对应字段并回读，不覆盖旧计划来掩盖错误。新剪点/真实内容变化使用新锁定源区间重新检查，不能跨实际变化继承旧报告。

`boundaryReviewRequired`单列取整源边界、1–3帧短碎片及源区间交叠，不自动删短音节或宣告接缝合格。执行者结合当前语义、词头词尾、波形与时间尺复核；形成`boundary-review.json`：`timelineSha256`须等于报告的`inputs.timeline.sha256`，`reviewedItemIds`覆盖待查item，`note`说明实际判断，`evidence`列当前复核证据文件。该记录只用于绑定本轮边界复查，不冒称听辨；导入记录会拒收缺少该复查的报告。

## 封面来源绑定

沿用本条run的`objectId`、`revision`与九项包装目标；在实际封面检查后准备`cover-source.json`。每个文件凭证使用`{"path":"实际文件路径","sha256":"该文件实际SHA256"}`，相对路径以计划文件所在目录解析：

```json
{
  "objectId": "当前对象ID",
  "revision": "r1",
  "sourceRevision": "r1",
  "sourceKind": "treated_frame",
  "source": {"path": "treated-still.png", "sha256": "实际SHA256"},
  "cover": {"path": "final-cover.png", "sha256": "实际SHA256"},
  "treatments": {"beauty": {"preset": "本条实际预设"}, "grade": {"contrast": 5}},
  "treatmentEvidence": {"path": "native-treatment-readback.json", "sha256": "实际SHA256"},
  "visualConfirmed": true,
  "visualEvidence": {"path": "cover-review.json", "sha256": "实际SHA256"}
}
```

示例的预设与调色仅展示字段，不是新参数目标。`treatments`逐项继承本条`requirements`中实际要求的`beauty/body/grade.target`，只排除表示主片覆盖数量的`mainClips/personClips`；不需要的项不填。处理依据与视觉凭证复用已有真实回读、截图及检查，不为这一步另造生产快照或导出视频。`visualConfirmed=true`只能在实际看过来源与最终封面后记录，脚本不识别图片是否真的美化。

`sourceKind`为已处理帧`treated_frame`、本次明确无处理要求的原帧`raw_frame`或纯动画`animation`。本人另选来源时用`approved_separate`，另存`exceptionReason`及带SHA的`authorization`文件凭证；例外只限本条授权，不能用一段AI解释代替本人决定。源图不能与最终封面是同一文件。

```bash
python3 scripts/manage_video_editing_run.py cover-source --record run.json --plan cover-source.json
python3 scripts/manage_video_editing_run.py verify --record run.json --key cover --actual actual-cover.json --evidence final-cover.png --evidence cover-review.json --scope '当前修订封面来源、处理继承及实际画面复查'
```

`cover-source`将结果写入原run的`editingExecution.coverSource`，新绑定只清除封面的旧检查。退出0为来源绑定成立，1为缺失／不符，2为输入错误；失败不进入封面验证。`verify`必须携带绑定的同一最终封面文件；没有来源绑定、换图、源修订不符、处理目标不符、凭证变化均拒绝。`checklist`每次回读来源和证据哈希，不用旧绿灯放行。它只验绑定与声明目标，不替代执行标准中的真实视觉检查。

## 工程依赖检查

从当前工程、真实应用配置与当前素材记录读取路径，复用原记录，不猜固定盘名。计划文件`dependency-plan.json`绑定`objectId`、`revision`、`route`和`basis`，其中`basis`是实际工程／配置来源文件的路径与SHA列表；不要用当前仍在写入的run本身作依据，否则更新run会让凭证失效。`paths`逐条列出实际依赖，每项为：

```json
{
  "id": "main-source",
  "role": "source",
  "path": "/实际原片.mp4",
  "kind": "file",
  "access": "read"
}
```

素材`role=source`按实际文件逐个列出，不能以素材根目录代替；已保存剪映草稿用`project`，真实缓存目录用`cache`，输出目录用`export`，后三类均为`kind=directory, access=readwrite`。同一角色可以有多项，`id`唯一。目录必须实际存在；未创建的最终文件以其真实现有父输出目录核对。不得为让预检通过而创建缺席盘名目录、穿过断链写入或更改全局配置。

`route=formal_native`分开检查：`source_read`需要素材，`native_handoff`需要素材／草稿／缓存，`native_export`另需输出目录。`route=local_review`只检查素材读取和本地审看所需素材／缓存／输出，两个原生阶段均为`not_checked`，不是通过；该路线不自动授权切换交付方式。

```bash
python3 scripts/inspect_video_editing_environment.py --dependency-plan dependency-plan.json --object-id 当前对象ID --revision r1 --budget-plan remaining-capacity.json > dependency-report.json
```

结果分别保留`capacityStatus`、`dependencies.stages`、逻辑路径及已解析目标。未传计划的旧`--path`调用仍只能证明容量观察，依赖为`not_checked`。退出0只说明本次声明路径与容量通过，2为任一相关阶段路径／容量受阻，1为输入或检查不可用；先看分阶段结果，可独立的上游继续。工具不探测写入、不打开软件，文件系统可达不能当原生工程已正常打开。路径列表是否覆盖真实工程仍须执行者对照来源核实。

原生字幕绑定配置增加`dependencyReport`。绑定时及每次`next/request`都重新检查计划、依据、对象／修订、当前路径和目标草稿；本地审看报告、失效计划、断链及未覆盖的草稿都不能放行。已绑定的历史run不回填成历史通过；继续操作前完成真实本次预检，再调用下例仅更新依赖凭证，保留旧凭证历史、导入记录和包装，不重建工程。实际配置或保存文件变化后也只更新这一凭证；旧时间线、SRT或修订失效仍回原主责步骤，不能靠刷新依赖豁免。

```bash
python3 scripts/manage_native_video_handoff.py dependencies --record run.json --report dependency-report.json
```

## 剪映字幕导入与同工程恢复

`manage_native_video_handoff.py`在本条既有run内维护`nativeHandoff`，不控制软件，不自动导入/重开工程。先确认官方交接草稿已在剪映打开，当前几何检查有效，正式SRT已准备，再创建绑定配置：

```json
{
  "projectPath": "/实际已保存剪映草稿目录",
  "dependencyReport": "dependency-report.json",
  "timelineReport": "timeline-check.json",
  "boundaryReview": "boundary-review.json",
  "srt": "captions.srt",
  "expectedFrames": 300,
  "expectedCaptionCount": 10
}
```

上例两个数量仅展示schema，须替换为当前时间线实测帧数及SRT实际卡数；无边界疑点时可省略`boundaryReview`。路径相对当前工作目录解析。绑定核对计划SRT数量/时长、几何报告与所有输入哈希，不跨修订、来源或剪点改变复用：

```bash
python3 scripts/manage_native_video_handoff.py bind --record run.json --config native-binding.json
python3 scripts/manage_native_video_handoff.py observe --record run.json --observation native-observation.json --evidence native-ui-readback.json
python3 scripts/manage_native_video_handoff.py next --record run.json
```

`native-observation.json`写实际观察：`windowReadable`、`projectPath`、`durationFrames`、`captionCount`、`captionResourceReady`、`captionsOnTimeline`、`saved`、`resourcesSufficient`。`captionResourceReady`只表示精确SRT资源已进素材库；`captionsOnTimeline`及`captionCount`另据真实时间线/当前原生字幕导出核对，不能据计划数量推定。未知字段明确为`null`，会阻止变更；不能以0代替未知。证据文件是本次真实UI回读/截图，不用工具输出冒充原生观察。

按`next`返回执行唯一动作。真正执行导入SRT资源、添加字幕轨或重开工程前，分别登记一次请求：

```bash
python3 scripts/manage_native_video_handoff.py request --record run.json --action import-resource
python3 scripts/manage_native_video_handoff.py request --record run.json --action add-captions
python3 scripts/manage_native_video_handoff.py request --record run.json --action reopen
```

三条不是连续执行清单，只执行当前`next`允许的一项，实际动作后重新`observe`。请求已登记、结果尚未知时返回`observe_pending_outcome`，不能重发加号、拖拽、导出草稿或重开命令。已有完整字幕时返回`reuse_captions`，直接续接未完成包装；部分字幕、错工程、总时长不符、输入/证据变化或资源不足返回阻塞，不新增第二轨。

一次添加已确认为0卡且正确SRT资源存在，先确认当前工程保存和容量，再允许重开同一已保存工程一次；不要求重启整个应用，不重新导出相同上游草稿。回读正确工程后仅允许再添加一次，仍未出现即停止字幕导入分支并保留检查点。其他应用故障仍按Skill既有恢复及时间上限，不因此增加重启次数。工具只维持导入请求/结果，未变化的音量、美颜美体、调色、身份、封面检查点不被清空；来源/速度或实际时间线变化应进入对应新修订记录。

## 剩余容量预算与文件检查

资源工具优先使用完整计划：

```bash
python3 scripts/inspect_video_editing_environment.py --path cache-directory --path export-directory --min-free-gb 5 --budget-plan remaining-capacity.json
```

计划为`{"items":[...],"excluded":{...}}`。每项含唯一`label`、`kind`、已存在的`directory`、`bytes`，或`duration_seconds`、`video_mbps`、`audio_kbps`，可指定正整数`copies`。`native_export`、`container_copy`、`retry_export`、`temporary`四类必须逐一列入，或在`excluded`说明当前剩余阶段为何不需要；不得同时列入又排除。还计入真实需要的动画媒体、交接副本、缓存与校验文件。原生导出需保留、容器修正另生成文件时，两个文件都占容量；重试估算另列，不能只预算交付文件。

已在磁盘的文件已影响实测空闲，不重复追加估算；若列入追踪则标记`already_present=true`及真实`existing_path`。同卷累计一次，各卷分别保留最低余量，不把外接盘空闲算给系统缓存卷，不预支可清理空间、APFS克隆或purgeable空间。纯质检阶段已完成的输出可以有据排除，不能把导出前预算缩成质检预算来获得通过。先检查是否能减少不必要的复制，再按既有清理授权处理；本工具不删除媒体、不降低余量。

成片文件检查：

```bash
python3 scripts/check_video_export.py --video native.mp4 --spec export-spec.json --output-dir file-qc
```

`export-spec.json`含当前Skill目标`width`、`height`、`fps`（如`30/1`）、`video_codec`、`audio_codec`、`sample_rate`、`color_space`，已知最终帧数时填`expected_frames`。工具读取真实容器与编码流、逐帧时间戳和帧数，完整解码并列黑帧候选。码率及其他未列入的字段仍按Skill回读，不把此检查误称全部参数已验。

仅当原文件只是MOV容器不符、其余检测正确时，可在预算已通过后增加`--remux-to new-final.mp4`：保留原文件，原编码流复制，核对音视频流哈希一致并重新完整解码。目标已存在即拒绝覆盖。缺帧、非恒定帧率或其他参数错误不得靠封装、补帧或改扩展名掩盖，应返回原生导出。修正后的最终文件仍须实际全片播放；黑帧候选需视觉判断，不自动作为错误或忽略。

## 分段计时

开工锁定对象/修订后、首次资源与工具预检前就调用`begin`；它允许包装目标暂未齐备，不要求先做完整字幕或封面。之后原有`init --requirements`只补目标，不重置已记时段：

```bash
python3 scripts/manage_video_editing_run.py begin --record run.json --revision r1 --phase preflight --category active
python3 scripts/manage_video_editing_run.py timer-switch --record run.json --phase chatcut_semantics --category active
python3 scripts/manage_video_editing_run.py timer-switch --record run.json --phase native_wait --category wait
python3 scripts/manage_video_editing_run.py timer-stop --record run.json
python3 scripts/manage_video_editing_run.py summary --record run.json
```

阶段按实际命名，类别为`active`主动操作、`wait`软件/工具或资源等待、`rework`修复已有错误；等待工具/用户时及时切出主动操作。意外磁盘/窗口故障发生时立即切换到fault_前缀的阶段，恢复后回到原步骤；不把故障恢复排入正常必经流程。`timer-switch`在同一写入内先停后开，避免漏关或重叠；停止后重新计时使用`timer-start`。脚本机器耗时另列，不叠加为AI主动时间。

跨独立CLI使用UTC起止时间计算区间，不持久化进程相对monotonic来跨进程相减；同进程仍交叉核对monotonic，可读取启动标识时检查重启。时间回拨、可识别重启或旧版开放计时保留未验证；使用`timer-abandon --record run.json --reason '实际原因'`将失败区间原样留档为未知，再从当前时点开始，不能补造过去时长。启动标识不可用会明确记录，跨进程前向系统时钟变化不能保证完全检出；不将UTC计时冒称更强的时钟验证。未记历史与未计类别为未知而非0，不能用总墙钟时间估算提速比例。


汇总沿用现有计时接口，分三项且不重叠：正常制作为非fault_阶段的active和wait；流程返工为非fault_阶段的rework；意外故障为全部fault_阶段（保留内部实际active/wait/rework类别）。正常效率口径为正常制作加流程返工，三项合计为已覆盖的交付总耗时。字幕错位、漏词和重复轨等流程错误归返工，不能剔除为意外。历史混合阶段不能精确拆分时标近似，不事后补造时间或用只扣新版故障的数字证明提速。
